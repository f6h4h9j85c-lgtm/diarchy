# diarchy rendering spec (protocol_version: 1)

How the store renders `chat.md`, `decisions.md`, and `goal.md`. These three files are the only thing a human normally reads, usually in Obsidian on a phone. The renderer is deterministic: same goal directory, same bytes. Where this document and the samples in `docs/samples/` disagree, the samples win and this document has a bug.

Normative words: MUST, MUST NOT, MAY.

## 0. Fixed by PROTOCOL.md 2.3

The renderer MUST keep these; nothing below relaxes them.

- Line 1 of every rendered file is exactly `<!-- generated by diarchy; do not edit -->`.
- `chat.md`: `# Chat: <goal-id>`, then one block per message sorted by `(ts, seq)` ascending, blocks separated by `---`. Block header `**<from> → <to> · <TYPE> · <decision_id> · re <AC list> · HH:MM:SS**` with the decision segment omitted when absent; then the claim in italics if present, the body, and evidence as bullets `- <kind>: <key fields>`.
- `decisions.md`: a table with columns `id | ts | by | claim | basis | evidence | supersedes`, one row per accepted DECIDE.
- `goal.md`: `# <goal-id>`, the goal text, then `## Status` (phase, lead, challenger, updated), `## Acceptance Criteria` (id, criterion, status `open|passing|failing`), `## Tasks` (id, task, assignee, branch, status).

## 1. Rules shared by all three files

### 1.1 Markdown dialect

Target: Obsidian reading view (mobile and desktop) and GitHub file view, from one byte sequence.

- Callouts use the GitHub alert spelling, uppercase, alone on the line: `> [!NOTE]`, `> [!WARNING]`. Obsidian matches callout types case-insensitively, so both render a titled box; plain-text readers see a blockquote. Only these two types are ever used. No custom titles on the `[!…]` line (GitHub does not render them).
- Links are standard markdown links with paths relative to the goal directory: `[goal](goal.md)`. Wikilinks are never emitted (GitHub shows them as literal brackets).
- Every `---` separator has one blank line before and after it. A `---` directly under a text line would turn that line into a setext heading.
- Paragraph breaks are blank lines. The renderer never relies on soft line breaks (GitHub collapses them, Obsidian does not).
- Hard rule for all strings copied from messages (claim, body, task text, criteria, test commands, notes): a line beginning with `#`, `>`, `-`, `*`, `+`, `|`, a digit followed by `.`, or consisting only of `---`, `***`, `___` is prefixed with a backslash. Inside italics, `*` and `_` are backslash-escaped. Inside a code span, a string containing a backtick is wrapped in double backticks with a space inside: ``` `` a`b `` ```. Inside a table cell, `|` becomes `\|` and newlines become a single space.
- Protocol tokens are rendered literally and never translated or prettified: `EXECUTE`, `adopted-challenge`, `in_progress`, `request_changes`, `load-balance`. The file and the MCP error messages must agree word for word so a reader can search for either.
- No em dashes anywhere in renderer-authored text. Separator between segments on one line is ` · ` (space, U+00B7, space).

### 1.2 Time

- All clock times are UTC, as the protocol gives them. Message headers show `HH:MM:SS` (mandated). The strip, the question callout, and `## Status` add `UTC` after the time when the time stands alone.
- One local-time hint, in parentheses, follows the most recent timestamp in each file: `16:30:00 UTC (12:30 local)`. Local is the host timezone of the store process at render time, minutes precision. If the local calendar date differs from the UTC date, the hint carries the date: `(23:30 local, 2026-10-24)`.
- Dates are `YYYY-MM-DD`. Durations are whole minutes: `150 of 240 min`.

### 1.3 Message type glyphs

Every block header in `chat.md` and every message reference inside a callout starts with the type's glyph, one space, then the mandated bold header. The glyph precedes `**`, so the mandated form is intact. All nine are plain-text code points outside the Unicode emoji list; none will be swapped for a colour emoji by a phone font.

| Type | Glyph | Code point | Weight |
|---|---|---|---|
| KICKOFF | ▸ | U+25B8 | light |
| PROPOSE | ○ | U+25CB | light |
| CHALLENGE | ▲ | U+25B2 | heavy |
| DECIDE | ● | U+25CF | heavy |
| ASSIGN | ↦ | U+21A6 | light |
| STATUS | ◇ | U+25C7 | light |
| DONE | ■ | U+25A0 | heavy |
| BLOCKED | ✕ | U+2715 | heavy |
| ASK_HUMAN | ⚑ | U+2691 | heavy |

Routine traffic is light and open; the five moments a human cares about are filled or crossed. No other glyph is used anywhere in the three files. Test results and review verdicts use words, not glyphs (1.5).

### 1.4 Budget line

Used in the strip (`chat.md`) and under `## Status` (`goal.md`). Values come from `budget.json` as of the last accepted message.

```
<used.messages_total> of <limits.messages_total> messages (PLAN <used.plan_messages> of <limits.plan_messages>) · <used.wall_clock_minutes> of <limits.wall_clock_minutes> min
```

If `limits.spend_usd` is set, append ` · <used.spend_usd> of <limits.spend_usd> USD` with two decimals. If `deadlock_watch` is non-null, append ` · open <decision_id>, DECIDE due by <deadline HH:MM:SS> UTC`.

### 1.5 Evidence items

One bullet per item, in message order, exactly `- <kind>: <key fields>`:

| kind | Rendering | Notes |
|---|---|---|
| commit | `` - commit: `9f3c2ab` `` | first 7 characters of `sha`, lowercase |
| pr | `- pr: [acme/api#412](https://github.com/acme/api/pull/412)` | link text per 1.6 |
| test | `` - test: `npm test -- rateLimit` · pass `` | result word: `pass` plain, `**fail**` bold, `pending` plain. If `log` is present append `` · log `.diarchy/logs/replicas.txt` `` |
| file | `` - file: `src/middleware/rateLimit.ts` `` | |
| review | `- review: [acme/api#412](https://github.com/acme/api/pull/412) · approve` | verdict word: `approve` plain, `**request_changes**` bold |
| human | `- human: human DECIDE 14:52:10` | derived from the cited message id: `<from> <TYPE> <HH:MM:SS>` |
| external | `- external: [docs.redis.io/commands/incr](https://docs.redis.io/commands/incr) · <note>` | ` · <note>` only if present |

The negative outcome is the bold one in every pair so a failing test or a rejected review is what the eye lands on when scrolling.

### 1.6 Link text for URLs

- `https://github.com/<owner>/<repo>/pull/<n>` renders as `<owner>/<repo>#<n>`.
- `https://github.com/<owner>/<repo>/commit/<sha>` renders as `<owner>/<repo>@<sha[0:7]>`.
- Any other URL renders as the URL without scheme and without a trailing slash, cut at 60 characters with `…` if longer.

### 1.7 Message references

When one message points at another (`reply_to`, the `human` evidence kind, the question callout), the reference is `<from> <TYPE> <HH:MM:SS>` in plain text, for example `codex CHALLENGE 14:04:55`. No link: the referenced block is in the same transcript, and the time string is unique within a goal and searchable. Message ids (filenames) never appear in rendered text, except as link targets in `decisions.md` (3.3).

## 2. chat.md

Order of the file:

1. generated-by comment
2. `# Chat: <goal-id>`
3. the strip (2.1)
4. `---`
5. message blocks (2.2), separated by `---`, with phase headings (2.3) and day headings (2.4) inserted between blocks

### 2.1 The strip

One callout, four paragraphs, right under the title. It is the only part of the transcript that is rewritten in place; everything below it is append-only in practice.

Callout type: `> [!WARNING]` when `phase` is `BLOCKED`; `> [!NOTE]` otherwise. That is the only thing the callout colour means: the human is needed, or not.

Paragraph 1, state:

```
**<PHASE>** · <human slot> · lead <lead> · challenger <challenger>
```

- `<PHASE>` is the literal phase. In BLOCKED it is `**BLOCKED** from <blocked_from>`.
- `<human slot>` is `no action needed` in PLAN, EXECUTE, DONE, and `**human needed** since <HH:MM:SS> UTC` in BLOCKED, using the ts of the latest ASK_HUMAN.
- With three or more agents, `challenger` lists them comma-separated.

Paragraph 2, budget line (1.4).

Paragraph 3, latest:

```
<YYYY-MM-DD> · last <HH:MM:SS> UTC (<HH:MM> local) · <from> <TYPE>: <summary>
```

`<summary>` is the claim if present, else the first line of the body, else empty (and the trailing `: ` is dropped). Cut at 80 characters on the last whitespace before the limit, with `…` (U+2026) appended when cut. The date is the UTC date of the last message.

Paragraph 4, navigation:

```
[goal](goal.md) · [decisions (<n>)](decisions.md)
```

`<n>` is the number of rows in `decisions.md`. In BLOCKED the paragraph begins `Question and how to answer: ` before the goal link.

Example, EXECUTE:

```
> [!NOTE]
> **EXECUTE** · no action needed · lead claude · challenger codex
>
> 14 of 80 messages (PLAN 5 of 12) · 109 of 240 min · open D1, DECIDE due by 15:59:12 UTC
>
> 2026-10-25 · last 15:49:12 UTC (11:49 local) · codex CHALLENGE: A default of 100 requests per minute breaks the dashboard, which polls twice a second.
>
> [goal](goal.md) · [decisions (3)](decisions.md)
```

Example, BLOCKED:

```
> [!WARNING]
> **BLOCKED** from EXECUTE · **human needed** since 14:35:01 UTC · lead claude · challenger codex
>
> 9 of 80 messages (PLAN 5 of 12) · 35 of 240 min
>
> 2026-10-25 · last 14:35:01 UTC (10:35 local) · system ASK_HUMAN: codex is BLOCKED (external): staging REDIS_URL missing. The human has been…
>
> Question and how to answer: [goal](goal.md) · [decisions (2)](decisions.md)
```

Why there is no "latest messages" section: duplicating blocks breaks "one block per message", doubles every search hit, and costs a screen before the transcript starts. Paragraph 3 gives the newest message in one line; the phase headings (2.3) give the Obsidian outline and GitHub table of contents a jump target at every landmark, and the terminal `## → DONE` heading is always the last line of a finished run.

### 2.2 Message block

```
<glyph> **<from> → <to> · <TYPE>[ · <decision_id>] · re <AC list> · HH:MM:SS**

[<fields line>]

[*<claim>*]

[<body>]

[- <kind>: <key fields>
- …]

[Tasks:
- T<n>: <task>
- …]

[Acceptance criteria added:
- AC<n>: <criterion>
- …]
```

Each bracketed part is present only when its data is present; parts are separated by one blank line. `<AC list>` is the `re` list joined by `, ` in message order. `<to>` is the literal `all`, `human`, or agent id (so a self-assignment reads `claude → claude`).

The fields line is plain text (no bold, italics, or code except for data values), segments joined by ` · `, in this order per type:

| Type | Fields line |
|---|---|
| KICKOFF | none |
| PROPOSE | `replying to <ref>` if `reply_to` present |
| CHALLENGE | `replying to <ref>` |
| DECIDE | `basis: <basis>` · `supersedes: <id>` if present · `replying to <ref>` if present · `budgets: <key> <value>, …` if present |
| ASSIGN implement | `` implement T<n> on `<branch>` `` · `new task: <text>` if `new_task` · `reason: <reason>` if present |
| ASSIGN review | `review <pr link per 1.6>` · `reason: <reason>` if present |
| STATUS | `T<n> <task_status>` if `task` present |
| BLOCKED | `kind: external · the human is paged` or `kind: internal · lead must ASSIGN or DECIDE` |
| ASK_HUMAN | `replying to <ref>` if present; `budget: <counter> <used> of <limit>` for budget-triggered |
| DONE | none |

`<ref>` is a message reference (1.7). The ASSIGN worktree path is not rendered; it is `<worktrees.root>/<agent>` by construction and the branch identifies the work.

Claim: the `claim` string wrapped in single `*`, as its own paragraph. Body: verbatim after the escaping in 1.1, as its own paragraph(s). Evidence: per 1.5. `Tasks:` and `Acceptance criteria added:` appear only on a `plan` DECIDE; the lead-in word is required so the list does not merge with the evidence list above it (two adjacent markdown lists separated by a blank line become one list).

### 2.3 Phase headings

A phase change is marked by an H2 placed immediately after the `---` that follows the message whose acceptance caused it:

```
## → <PHASE> · HH:MM:SS
```

with that message's time. One heading per transition, in this order of causes: KICKOFF → `## → PLAN`; `plan` DECIDE → `## → EXECUTE`; `BLOCKED kind: external`, deadlock, or budget exhaustion → `## → BLOCKED` (after the last accepted message; the system ASK_HUMAN then follows the heading); human DECIDE → `## → <blocked_from>`; DONE → `## → DONE`, which is then the last line of the file.

Headings are the only H2s in the file, so the Obsidian outline reads as the run's timeline: `→ PLAN`, `→ EXECUTE`, `→ BLOCKED`, `→ EXECUTE`, `→ DONE`.

### 2.4 Day headings

When the UTC date of a message differs from the previous message's, insert `## <YYYY-MM-DD> UTC` before its block (after the `---`, and after any phase heading placed there). Rare: a run is bounded by `wall_clock_minutes`.

### 2.5 Separator

Blocks, and the strip, are separated by a line containing exactly `---` with one blank line on each side.

## 3. decisions.md

```
<!-- generated by diarchy; do not edit -->
# Decisions: <goal-id>

<YYYY-MM-DD> UTC · <n> decisions, <m> superseded · [goal](goal.md) · [chat](chat.md)

| id | ts | by | claim | basis | evidence | supersedes |
|---|---|---|---|---|---|---|
| … |
```

### 3.1 Rows

One row per accepted DECIDE, sorted by `(ts, seq)`. The date line uses the UTC date of the first DECIDE; if later rows fall on another date, the `ts` cell of those rows is `YYYY-MM-DD HH:MM:SS`.

### 3.2 Cells

| Column | Content |
|---|---|
| id | the decision id the row created or closed: `plan`, `D1`. Wrapped in `~~ ~~` (strikethrough) once a later DECIDE names it in `supersedes`. The row itself is never removed or reordered. |
| ts | `HH:MM:SS`, linked to the message file: `[14:07:30](chat/20261025T140730Z-0004-claude-DECIDE.md)` (3.3) |
| by | sender id (`claude`, `codex`, `human`) |
| claim | the claim verbatim, table-escaped (1.1). The only column expected to wrap. |
| basis | the literal basis token |
| evidence | items joined by `; `, each as `<kind> <key>`: `commit` + short sha in code, `pr` + `#<n>`, `test` + result word (bold on fail), `file` + path in code, `review` + `#<n>` + verdict word, `human` + reference, `external` + link text. Empty when the DECIDE has no evidence. |
| supersedes | the decision id named in `supersedes`, or empty |

A chain reads downward: a struck id has a later row naming it. Only the direct ancestor is shown; longer chains are followed row by row.

### 3.3 The one place ids appear

The `ts` link opens the raw message file in `chat/`. That is the only place the renderer uses message ids in visible markdown, and it is a link target, not text.

## 4. goal.md

Order of the file:

1. generated-by comment
2. `# <goal-id>`
3. the question callout (4.1), only in BLOCKED
4. goal text (the kickoff body, verbatim)
5. navigation line: `[chat](chat.md) · [decisions (<n>)](decisions.md)`
6. `## Status` table (4.2) and the budget line
7. `## Acceptance Criteria` table (4.3)
8. `## Tasks` table (4.4)

### 4.1 The question callout

Present only when `phase` is `BLOCKED`. It is the first thing after the title, above the goal text. Always `> [!WARNING]`. Three to four paragraphs:

Paragraph 1, always:

```
**Human needed** since <HH:MM:SS> UTC (<HH:MM> local). The run is BLOCKED (from <blocked_from>); nothing moves until you answer.
```

Paragraph 2 and 3 depend on the trigger, read from the latest ASK_HUMAN and its `reply_to`:

External BLOCKED (`reply_to` is a BLOCKED message):

```
**<agent> is blocked (external), re <AC list>:**

> <BLOCKED body, verbatim, as a nested quote>
```

Deadlock (`reply_to` is a CHALLENGE; ASK_HUMAN carries `decision_id`):

```
**Deadlock on <decision_id>, re <AC list>.** <lead> did not DECIDE within 2 messages or 10 minutes. The two positions:

1. <proposer> PROPOSE <HH:MM:SS>: *<claim>*
2. <challenger> CHALLENGE <HH:MM:SS>: *<claim>* (test `<test>` · <result word>)
```

For a reopened thread, item 1 is the DECIDE that last closed it, labelled `DECIDE`.

Budget or clock (`reply_to` absent):

```
**Budget reached:** <counter> <used> of <limit>. Both agents are stopped.
```

Final paragraph, how to answer. The human never edits a vault file; the launcher posts for them. This callout, `diarchy status`, and the launcher's output are the only places a run shows the reply command; the ASK_HUMAN body never carries it (PROTOCOL.md 10), so a PM reading its inbox is not handed the human's command:

- external: `` **To answer:** run `diarchy reply "<your answer>"`. It is posted as a DECIDE with basis human, recorded in decisions.md, and EXECUTE resumes. `diarchy stop` ends the run and leaves it BLOCKED. ``
- deadlock: `` **To answer:** run `diarchy reply "<ruling>" --decision <decision_id>`. Your ruling closes <decision_id> as a DECIDE with basis human and <blocked_from> resumes. `diarchy stop` ends the run. ``

When the stalled decision is `plan` and another thread is still open, the command is `diarchy reply "<ruling>"` without `--decision` (a `plan` ruling would be rejected by PHASE_GATE); the paragraph then says the ruling is recorded as a new DECIDE and that the lead must DECIDE plan next.
- budget: `` **To answer:** run `diarchy reply "continue" --budget <counter>=<suggested>` to raise the limit and resume <blocked_from>, or `diarchy stop` to end the run. `` where `<suggested>` is twice the current limit.

The word `EXECUTE` in the external variant is `<blocked_from>` when the block happened in PLAN.

### 4.2 Status

```
| phase | lead | challenger | updated |
|---|---|---|---|
| <PHASE> | <lead> | <challenger> | <YYYY-MM-DD HH:MM:SS> UTC |
```

`updated` is the ts of the last accepted message. Directly below the table, one paragraph: the budget line (1.4), then ` · ` and the human slot from 2.1 (`no action needed` or `**human needed** since <HH:MM:SS> UTC`).

### 4.3 Acceptance Criteria

```
| id | criterion | status |
|---|---|---|
| AC1 | <criterion> | open |
```

Status is the literal token; `failing` is rendered `**failing**`. Status follows PROTOCOL 2.3: set by the latest `test` evidence item in a STATUS accepted in EXECUTE whose `re` includes the AC (`pass` → `passing`, `fail` → `failing`, `pending` → unchanged), `open` until one exists. `test` items in CHALLENGE, DECIDE, DONE, or a PLAN STATUS are probes or attestations and never change it. Criteria added by `ac_add` are appended in order.

### 4.4 Tasks

```
| id | task | assignee | branch | status |
|---|---|---|---|---|
| T1 | <task> | codex | `diarchy/20261025-rate-limit/codex` | assigned |
```

Branch in a code span; empty until an ASSIGN. Status is the literal token (`todo`, `assigned`, `in_progress`, `done`). Tasks from the `plan` DECIDE come first in order, then `new_task` tasks in message order. Review assignments do not appear in this table; they are visible in `chat.md` and as `review` evidence.

## 5. When files are rewritten

All three files are rewritten inside the transaction of every accepted message (PROTOCOL 2.2), and `goal.md` and `chat.md` are also rewritten when a store tick moves the phase to BLOCKED (the tick also posts the ASK_HUMAN, so this is the same event). They are not rewritten on ticks that change nothing but counters, so Obsidian Sync is not churned every 15 seconds. The budget line therefore reads "as of the last message", which the `updated` cell makes explicit.

## 6. Edge cases

- Long `re` lists wrap inside the bold header on a phone; this is accepted. Lists are never abbreviated to ranges, so searching `AC7` finds every message about it.
- A message with no claim, body, or evidence (an ASSIGN) renders as header plus fields line.
- A STATUS with both a task update and review evidence for another PR renders all of it; the fields line names the task, the evidence names the review.
- Multiple BLOCKED cycles produce multiple `## → BLOCKED` and `## → EXECUTE` headings; the strip always reflects the current state.
- A superseding DECIDE shows the new `D<n>` in its header and `supersedes: <old>` on its fields line; `decisions.md` strikes the old id.
- Three or more agents: the strip and `## Status` list challengers comma-separated; nothing else changes.
- If `budget.json` is missing or unreadable, the renderer still writes the transcript and replaces the budget line with `budget unavailable`; it never omits the strip.
